# Первая задача из своего репозитория

Работает из исходного checkout Fuse (`npm ci`, Node ≥22.19). Не нужен API-ключ. Этот режим проверяет **одну именованную синхронную функцию**: аргумент — строка, результат — строка или boolean. Код исполняется в QuickJS; нет Node API, загрузки runtime-зависимостей и доступа к вашему checkout. Это не запуск проекта и не импорт приватного репозитория в GitHub.

Готовый [внешний пример на реальном изменении slash](../examples/team-cases/slash-unicode/README.md) можно воспроизвести без подготовки файлов. Для ESM default export используйте `entry: "default"`.

## 1. Подготовьте две версии функции

Рядом с каталогом Fuse создайте локальный каталог `team-case`. Из двух проверенных командой ревизий скопируйте в него `before.ts` и `after.ts` с тем же именованным экспортом. При необходимости выделите самодостаточную функцию, сохранив её поведение; запишите исходный путь, ревизии и причину выделения в локальных заметках. Не берите ожидаемые ответы из нового кандидата.

## 2. Опишите баг и поведение, которое нужно сохранить

`target` — пример, на котором старая версия ошибается. `control` — пример, на котором она уже работает правильно. Укажите как минимум по одному примеру каждого вида.

Рассчитайте SHA-256 **байтов** файлов, например `Get-FileHash before.ts,after.ts -Algorithm SHA256`. Сохраните `case.json` рядом с файлами. Подставьте реальные хеши в нижнем регистре. Пример для функции `normalize`, исправляющей обработку пробелов:

```json
{
  "schema": "jevio-team-case/v1",
  "task": "Приведи метку к верхнему регистру, убери пробелы по краям и сохрани внутренние пробелы.",
  "entry": "normalize",
  "base": {"file": "before.ts", "sha256": "<sha256 before.ts>"},
  "gold": {"file": "after.ts", "sha256": "<sha256 after.ts>"},
  "checks": [
    {"kind": "target", "input": " build ", "expected": "BUILD"},
    {"kind": "control", "input": "a b", "expected": "A B"}
  ]
}
```

## 3. Проверьте задачу, затем кандидата

Вернитесь в корень Fuse. Последняя команда предполагает, что новое решение сохранено как `../team-case/candidate.ts` и экспортирует ту же функцию.

```sh
npm run eval:team -- qualify ../team-case/case.json
node scripts/eval-team.mjs input ../team-case/case.json
npm run eval:team -- verify ../team-case/case.json ../team-case/candidate.ts
```

| Команда | Как читать результат |
|---|---|
| `qualify` | `qualified: true` означает, что **каждый** `target` дал `FAIL` на `base` и `PASS` на `gold`, а каждый `control` прошёл на обеих версиях. Исключение вместо ответа не считается воспроизведением бага. |
| `input` | Печатает задание, имя экспорта и исходную версию функции. Эталон и проверки в вывод не входят. |
| `verify` | Сначала повторяет `qualify`. Если задача пригодна, проверяет кандидата: `verified: true` означает, что пройдены все примеры. Массив `results` соответствует порядку `checks` в `case.json`. |

Код выхода **0** — команда выполнена успешно; **1** — задача не воспроизводит нужное поведение или кандидат не прошёл; **2** — проверьте входные файлы и работу инструмента.

**Приватность:** `input` выводит исходный код в терминал. Не перенаправляйте его в общие логи и не отправляйте провайдеру без разрешения. Отчёты `qualify` и `verify` не содержат исходников и значений тестовых примеров.

Храните приватный каталог, кандидатов и отчёты у себя. Держите иные функции, недетерминированные результаты, npm-импорты, сеть и многофайловые патчи вне этого режима. Два верных примера не доказывают полную корректность: полезно показать контроль ошибочных «простых исправлений» ревьюеру до эксперимента. Пройденные локальные проверки не означают независимого человеческого принятия. Команда не измеряет расход, не запускает живые модели и не добавляет задачу автоматически в публичный каталог или сравнительный отчёт.
