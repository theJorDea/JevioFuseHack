# Jevio Fuse Model Evaluation — решение и план пилота

**Продукт:** Jevio Fuse helps engineering teams find the most cost-effective AI coding model for their own codebase through reproducible real-world evaluations. Покупатель — команда с действующим API-бюджетом, которой нужно принять решение о переходе между моделями. Активное направление одно. Handoff сохраняется, но работа над ним заморожена. В первый релиз не входят новый агент, облако, дашборд, уведомления и автоматический выбор «лучшей модели».

**Разделение ответственности.** Fuse владеет задачами, протоколом сравнения, проверкой результата и отчётом. Modelflare — предлагаемый первый шлюз для живого пилота, не спонсор и не подтверждённый партнёр. [Документация](https://docs.modelflare.dev/) подтверждает общий API. [Usage and cost](https://docs.modelflare.dev/guides/usage-and-cost/) указывает на фактические списания и группу маршрутизации в журнале консоли; это не обещание поля `cost` в каждом HTTP-ответе.

## Месяц: этапы и условия выхода

| Этап | Результат | Условие перехода |
|---|---|---|
| Неделя 1: измерение | Офлайн-квалификация задачи, фиксированный план запусков, проверяемая арифметика отчёта | Исходник воспроизводит ожидаемый сбой, эталон его устраняет; контрольные тесты на обеих версиях зелёные. Некорректные строки и пропущенные попытки отвергаются. |
| Неделя 2: набор и изоляция | 10–15 задач с описанием без подсказки, лицензией/согласием, pinned base и gold, хешами скрытых тестов и окружения | Проверить содержимое model-visible snapshot по allowlist. Никаких `.git`, конфигов с ключами, ссылок на gold, кэшей истории и чужих артефактов. Отдельный одноразовый изолированный исполнитель для **непроверенных** патчей, без хостовых секретов/сети. Карантин для нестабильных тестов. |
| Неделя 3: платный пилот | Две доступные версии моделей, 2–3 повтора на задачу, лог всех запросов и слепое ревью патчей | До старта — разрешение на передачу выбранных данных, проверка контрольного биллинга, зафиксированный лимит расходов и остановка до превышения. Не включать скрытую маршрутизацию на другие модели. Указывать неподконтрольные различия. |
| Неделя 4: решение и дистрибуция | Один воспроизводимый отчёт по собственному репозиторию + RU quickstart для сторонней команды | Отделить цену от качества; показать ошибки, выборку, неизвестные списания. Приватные материалы не публиковать. Предложить демо трём командам. Сигнал спроса — хотя бы одна предоставляет свои задачи и принимает решение, включая решение не переходить. |

## Правила до первого платного запуска

1. Для каждой задачи независимо подтвердить FAIL→PASS и PASS→PASS. Отказ запуска или ошибка инфраструктуры — не эквивалент ожидаемому красному тесту. Исторические публичные задачи помечать как потенциально известные модели. Не выдавать демонстрационные фикстуры за независимый набор.
2. Одна версия harness, prompt, инструменты, начальные байты, доступные ресурсы, температура/поддерживаемые настройки, timeouts, turn/token/billing limits. Меняется только модель. Digest всего фактически исполняемого окружения обязателен для публикации; SHA родительского коммита при грязном checkout недостаточен. Фиксировать immutable model ID или обозначать alias. Запуски чередуются в блоках задача × повтор. Одинаковый предел затрат — не одинаковое фактическое потребление.
3. Никакого запуска произвольного кода моделей в обычном процессе с правами пользователя. Агенту не давать сетевой поиск решения, хостовый shell или каталог проверяющего. Закрытые тесты — в независимом verifier, не в отправляемом snapshot. Защищать от изменения тестов и инфраструктуры. В офлайн-разработке допускается запуск только доверенных, вручную проверенных контрольных случаев.
4. Хранить неизменяемые идентификаторы plan/task/attempt, snapshot, verifier и патча. На каждую попытку журналировать все billed requests и retries, пропуски, timeout и ошибки сервиса, время, расход и маршрут. В итоговой матрице каждая запланированная попытка представлена; не выбрасывать проигрыши. Неуспех, регрессия и неисполненная проверка различны. Отдельно считать непроверяемые случаи. Не утверждать отсутствие регрессии при непройденном этапе проверки.
5. Основная единица статистики — задача, повторы одной задачи не независимы. Дать долю verified **попыток**, количество разных задач и разбивку по повторам; также показывать распределение парных различий по задачам и неопределённость до рекомендации. Не трактовать один успех из трёх как три исправления трёх разных багов. Проверенное исправление проходит скрытую проверку и контрольные тесты. Принятое — отдельное решение ревьюера, по возможности без знания модели. Для пилота фиксировать знаменатель и покрытие ревью. Время не смешивать с финансовой метрикой.
6. Стоимость проверенного/принятого результата = сумма **всех** расходов модели (включая неудачи и повторы) / число verified/accepted попыток в описанной политике. Отдельно указывать, если расчёт делается на уникальную задачу. Источник — сверенные расходы шлюза; оценки по тарифу отдельно. Неизвестные расходы не равны нулю. Нулевой знаменатель или неполное ревью для итоговой accepted-цены → н/д. При малом числе задач — описательный отчёт, не маркетинговый рейтинг.

## Очередь для ручной квалификации (не результаты)

Первичный просмотр истории Jevio даёт кандидатов: `dfcd533` (восстановление активной задачи после reload), `3a20238` (совместимость test runner между версиями Node), `c0ae5d5` (совместимость поля temperature), `65e3ea4` (восстановление текстовых вызовов инструментов). Это ссылки для куратора, не часть промпта. На каждый случай получить стабильный поведенческий тест и отдельно оценить затраты на окружение. Серия соседних исправлений одной ошибки не считается независимыми задачами. Не добирать количество косметическими изменениями.

## Предложение Modelflare — черновик, не отправлено

[Условия программы, §2](https://modelflare.dev/partner-program-terms): нужны точные URL, позиция и формат; квоты из размещения не следуют. Предлагаемое место после публикации: `https://github.com/theJorDea/JevioFuseHack/blob/main/docs/model-evaluation.md`, раздел подключения пилота, текстовая ссылка «API и фактические списания: Modelflare» с раскрытием поддержки рядом. До публикации не указывать как действующее размещение.

Предложить Malachi пилот двух моделей на одинаковых задачах, публичный RU quickstart в документации Fuse и явное упоминание шлюза в разделе подключения и в отчёте пилота. Взамен обсудить каталог/Project Plaza и отдельную тестовую квоту с жёстким потолком. Сверить актуальные письменные условия и право на логотип перед размещением. Стандартное размещение не закладывается в бюджет как источник кредитов или трафика; affiliate оформляется отдельно. Если пилот субсидирован — раскрыть поддержку, показать стоимость по биллингу до субсидии и не обещать желаемого победителя. Без согласия владельца кода никаких внешних отправок.

## Как попробовать из checkout (Node 22.19+)

```sh
npm run eval:qualify   # только проверка доверенного контрольного случая
npm run eval:qualify -- --all  # весь исторический набор, без API
npm run eval:demo      # квалификация всего набора + синтетический пример сравнения
npm run eval -- plan manifest.json
npm run eval -- report manifest.json ledger.json
```

Манифест для `plan`: `models` (различные ID), `tasks` (объекты `id`, `caseSha256`), `repeats`, `provider`, `routingGroup`, `systemPrompt`, `harnessRevision` (40 hex), `tools`, `timeLimitSec`, `maxIterations`, `maxOutputTokens`, `temperature`, `maxCostMicros`, `seed`. Для живого исследования хеш кейса должен включать snapshot, проверки и условия задачи. `plan` ничего не исполняет: возвращает очередность, SHA-256 плана и **теоретический** потолок в миллионных долях USD; пока не является ограничителем расхода API.

`report` принимает JSON `{schema: "jevio-eval-ledger/v1", source: "simulation" | "operator-import", currency: "USD", planSha256, rows}`. Одна строка — `model`, `task`, `repeat` (с 1), `verified`, `regression` (null = не проверено), `accepted` (null = нет ревью), `costMicros` (null = неизвестно), `durationMs`. Полный исполняемый пример формирования обоих файлов: `scripts/eval-demo.mjs`. Импорт проверяет матрицу и арифметику, **не аутентифицирует** счета, патчи или результаты. `source: simulation` явно помечает таблицу. Успех эталона при квалификации — наблюдение о тесте, не результат модели.

## Проверка кандидата: формат пакета и границы изоляции

`npm ci`, затем `node scripts/eval-candidate.mjs input` печатает единственный пакет для модели: описание и исходный `src/task-intent.ts`. Не давайте агенту сам checkout, Git, shell или каталог тестов. Сохраните ответ модели как полный файл, не unified diff, и выполните `npm run eval:candidate -- verify candidate.ts`. Для локальной самопроверки можно подставить исторический `benchmark/evaluation/task-intent-questions/gold-task-intent.ts.fixture`. Код выхода 0 — обе поведенческие проверки пройдены, 1 — не пройдены, 2 — ошибка входа или проверяющей инфраструктуры.

Исполнитель поддерживает синхронные классификатор и парсер текстовых вызовов. Для парсера укажите `text-tool-line-continuation` после `input` или `verify candidate.ts`. Вердикт сравнивает имя вызова и полные аргументы для LF, CRLF и корректного ввода; сами вызовы инструментов никогда не выполняются. Для каждого входа запускается отдельный процесс с очищенным окружением: Node снимает типы, а JS исполняется в QuickJS/WASM без загрузчика модулей, файловых, сетевых и shell-API. Вход теста доступен функции, ожидаемый ответ остаётся у родителя. Для гостя заданы лимиты памяти и времени, родитель прерывает зависший worker. Сбой worker не засчитывается как поведенческий FAIL. Никакого запасного запуска через Node. Два публичных примера — проверка механики, не защита от подгонки и не human acceptance. Это локальный прототип, не универсальная мультиарендная песочница; произвольный npm-проект или реальную сеть этот режим не запускает. В задаче `node-test-isolation-flag` вход и выход — JSON-набор из package.json и необязательного файла раннера; версия Node и дочерний процесс представлены ограниченными двойниками. Проверяется выбор аргументов и передача exit status, а не запуск второй версии Node. В `provider-stream-recovery` проверяется последовательность запросов и текст при прерванном и здоровом SSE-потоке; в `web-reload-busy` — первоначальное состояние чата, а не визуальный рендер или поздний polling. Для Cognee и LM Studio используются проекции исторического исходника, а не действующие облачные сервисы.

## Репетиция пилота без доступа к моделям

Из checkout: `npm run eval:rehearse -- ../rehearsal-001`. Нужен новый каталог. Репетиция проверяет все 10 исторических задач и строит план для двух имён моделей × двух повторов на каждую (40 попыток). В историческом случае Kimi модель возвращает полный модуль провайдера. Проверяется сформированный запрос: исправление должно менять температуру для Kimi и сохранять настройки других моделей, не обращаясь к настоящему API. Для picker-входа заменяют сам метод класса; для loader-входа возвращают показанные члены класса (конструктор и два метода), без оболочки нового модуля. Проверяются и пустой индикатор в состоянии покоя, и активная анимация при незавершённом запросе. Раннер обрабатывает заранее заданные Chat Completions ответы **без сети**. Успех вычисляется проверкой возвращённого исходника, а не записывается заранее. В числе ответов — неисправленный код, код с регрессией и HTTP 503. Неудачи остаются в знаменателе. Вход модели не содержит эталон. Генератор *подставного* ответа имеет эталон — для проверки самого конвейера, не качества модели.

После каждой завершённой попытки записывается `attempts.jsonl`, затем `ledger.json` и `report.md`. `node scripts/eval-recover.mjs DIRECTORY` проверяет привязку строк к плану и восстанавливает журнал только при полном совпадении матрицы. Если процесс остановился посреди строки, показывает последнюю завершённую попытку и число ненаблюдаемых результатов; не придумывает их и не отправляет запрос повторно. Неполный журнал не есть законченный сравнительный отчёт. Каталог повторно не используется; авторезюмирования или повторной отправки запросов нет. Для сверки: `node scripts/model-eval.mjs reconcile ../rehearsal-001/manifest.json ../rehearsal-001/ledger.json ../rehearsal-001/synthetic-receipts.json`. Команда выводит новый JSON, оригинал не меняется. Вход чеков — массив `{requestId, model, currency:"USD", costMicros}`; это формат импорта Fuse, **не заявление о формате экспорта Modelflare**. Не сопоставлять по приблизительным timestamps или названию модели. До live-пилота требуется подтвердить на разрешённом запросе, что ID шлюза можно связать с реальным списанием. Стоимость отсутствующего чека остаётся неизвестной, включая запросы с ошибкой. `ledger.source` остаётся `simulation` после сверки. Без настоящих платежных записей и человеческого ревью вывод о выгодности не делаем.

## Ручное ревью результата

В новой репетиции `blind-review.json` содержит проверенные варианты без имён моделей, цены и порядка попыток. Одинаковые байты внутри одной задачи показываются один раз; файл содержит исходники, поэтому остаётся локальным. Ревьюер сопоставляет вариант с исходным заданием и пишет `{planSha256, decisions:[{task,candidateSha256,accepted:true|false}]}`. `node scripts/model-eval.mjs review MANIFEST.json LEDGER.json DECISIONS.json` печатает новый журнал: решение относится только к уже проверенным попыткам той же задачи с теми же байтами. Противоречивые решения отклоняются. Отсутствие решения не равно отказу. Это маскировка метаданных, не гарантия, что автора нельзя угадать по стилю кода. Сам факт создания пакета не означает, что человек его прочитал.

## Статус разработки

Существующий `scripts/coding-benchmark.mjs` измеряет Cognee off/on по подстрокам в файлах. Это отдельный эксперимент, не доказательство корректного исправления и не средство изоляции. Новая линия не использует этот раннер для сравнения моделей. Каталог доверенных тестов: потеря data ID Cognee, температура исходящего запроса Kimi, ошибочная классификация вопроса как команды редактирования, восстановление активного чата после перезагрузки, обработка переноса строки в текстовом вызове инструмента, выбор флага изоляции Node при разных возможностях раннера и возврат фокуса при закрытии списка сессий. Каждая имеет собственное описание, точные байты base/gold и отдельную поведенческую проверку. `caseSha256` связывает идентификатор, текст задания, обе версии исходников и проверку. Все примеры публичные: пригодны для отладки и демонстрации, но не доказывают отсутствие обучающей утечки. Ещё три задачи проверяют настройки LM Studio, восстановление прерванного стрима и отображение статуса загрузки. Итого 10 квалифицированных исторических случаев, все 10 поддерживают проверку произвольного ответа в QuickJS. Это воспроизводимый офлайн-предпилот, не сравнение живых моделей. Нет сверки реальных счетов или независимого человеческого вердикта.
